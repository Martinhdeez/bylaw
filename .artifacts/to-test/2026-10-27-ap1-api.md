# AP1 — FastAPI app, report store, ratified store

Item AP1, iteration 03 (`docs/plan/03-product/`). Requirements REQ-AP1-1..5, contracts C9 and C10 (v1, v1.1, v1.2), and the C4 v1.7 report lists (contract 01).

## Problem

The engine only runs from the CLI. The web app (UI2) and the demo flow need an HTTP API: list domains, read the policy, open the latest report and a hole, run an audit in the background and watch its progress, ratify an amendment, and read the bench. Nothing provides C9 or the C10 ratified store, so REQ-AP1-1..5 have nothing to check against.

## Root cause

This is a new feature, so there is no defect. The missing pieces were:
- `bylaw/__main__.py:66`: the only entry point is the CLI. There is no `bylaw/api.py`.
- `bylaw/report.py:73` (`audit`): runs synchronously and has no progress hook.
- `ratified/` and `bylaw/ratified.py` did not exist.

## Change

- `bylaw/ratified.py` (C10): `load`, `ratify`, `effective_ruleset`. The store lives at `ratified/<domain>.json` under the repo root, or under env `BYLAW_RATIFIED_DIR`, which is read on every call (v1.1).
  - Ratifying is idempotent by `hole_key`. The read-modify-write runs under a module `threading.Lock` (review of PR #11).
  - Before writing, the patch is applied on top of what is already ratified. A rule id that collides raises `ValueError` and nothing is written (the API answers 409).
  - `bylaw.amend.apply` is imported lazily. Until AM1 lands, a local fallback with the same C7 behaviour is used (append, pure, refuse colliding ids).
- `bylaw/api.py` (C9): every endpoint in the table.
  - Domain is a `Literal`, so an unknown domain gets 422. `budget >= 1`.
  - `latest` is the newest file by mtime among `<BYLAW_REPORTS_DIR>/<d>.json` and `<BYLAW_CACHE_DIR>/<d>-*.json`, both read per request. There is no in-memory latest (v1.1).
  - `/api/holes/{key}` searches `holes`, `contradictions` and `ambiguities` (Class A, B, C). Each object keeps its `class`.
  - Ratify answers 404 for an unknown key and 409 when the hole has no amendment.
- Background audit runner:
  - Runs in a daemon thread and calls `bylaw.report.audit` unchanged.
  - The domain is wrapped in a call-counting proxy, so search progress (`tool_calls`, at most one event every 0.5 s) arrives without touching `report.py`.
  - Phases: `compile` (the hand RuleSet; no compile step runs), `search`, `verify`, optional `amend`/`backtest`, then `done` or `error`. `tokens` and `llm_calls` are deltas of `bylaw.llm.USAGE`.
  - `amend: true` with `use_llm: false` is skipped with an event, because drafting needs Muse and the offline guarantee holds. When `bylaw.amend` is missing, the step is also skipped with an event.
- SSE: `StreamingResponse` (no sse-starlette). Late subscribers replay every past event. The stream ends after `done`/`error` and sends a keepalive comment every 15 s.
- Static: `/{path}` serves `web/dist` files, falling back to `index.html`. `/api` and `/api/*` are never swallowed (404). Paths are confined to `dist`.
- Dependencies: `fastapi`, `uvicorn` (runtime) and `httpx` (dev, needed by TestClient).

## Out of scope / not done

- The `closes` field is an approximation: true when the patched RuleSet blocks the hole's own chain. C7's "re-audit of the goal finds 0 holes" should come from AM1's report helper once it merges.
- A Muse audit (`use_llm: true`) ends in `error` until PR1 merges, because `proposer.search` raises `NotImplementedError`. A retail audit errors for the same reason (no BFS move set). Both are EX1/PR1 scope.
- `tool_calls` in events counts every executed tool call, including the 5 verifier replays per candidate. The report's `stats.tool_calls` counts search steps only.
- `llm.USAGE` is process-global. Two concurrent Muse audits would share counters.
- Audit jobs live in memory and are lost on restart. Their reports persist in the cache dir.
- Not measured: a live Muse run, the Playwright smoke test (UI2), and behaviour with several concurrent SSE clients beyond the two sequential subscribers in the transcript.
- Rebased onto `bylaw/build` after EX1 (#9) merged. The merged `report.py` does not emit `contradictions` yet (01 v1.7 is pending in EX1/PR1). The API reads the list when it is present and amends Class B entries along with the holes.
