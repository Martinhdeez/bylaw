## Title

Airline gold tasks 7 and 32 use upgrade-first chains to get around basic economy restrictions; retail cancel after a payment change refunds more than was paid

## Body

Hi, and thank you for τ²-bench. We are a team at the Meta Global AI Developer Hackathon, building a tool that checks agent policies by executing tool-call chains in the τ² environments. While cross-checking against the gold trajectories, we found two airline tasks where the policy text and the graded behaviour seem to disagree, one gap in the airline policy, and one retail tool behaviour that refunds more than was paid. All references below are to commit `0c69df4`.

We may be misreading the intended policy. If these chains are intended, a sentence in `policy.md` would make that explicit for agents and for anyone auditing them.

### 1. Airline task 7: upgrade a basic economy reservation to business, then cancel it

`data/tau2/domains/airline/policy.md`:

> L143-147: "Otherwise, flight can be cancelled if any of the following is true:
> - The booking was made within the last 24 hrs
> - The flight is cancelled by airline
> - It is a business flight
> - The user has travel insurance and the reason for cancellation is covered by insurance."

> L117: "In other cases, all reservations, including basic economy, can change cabin without changing the flights."

Reservation `XEHM4B` (from `db.json`) is basic economy. It was created on 2024-05-01T05:17:41, more than 24 h before the policy clock, and has `insurance: "no"`. As booked, it meets none of the four conditions. The task's user instructions (`tasks.json` L363) are: *"ask to upgrade to business first and then cancel the reservation"*. The gold actions (`tasks.json` L390, L410) are:

- `7_2` `update_reservation_flights(reservation_id="XEHM4B", cabin="business", flights=[HAT005 2024-05-20, HAT178 2024-05-30], payment_id="credit_card_2408938")`
- `7_3` `cancel_reservation(reservation_id="XEHM4B")`

When we replay these actions, the upgrade charges 1,072 and the cancel refunds 296 + 1,072. The original non-refundable basic economy fare comes back in full. Each step is allowed on its own. Whether "It is a business flight" means the cabin at booking time or at the time of cancellation is not stated.

### 2. Airline task 32: upgrade basic economy to economy, then change the flights

> L110: "Basic economy flights cannot be modified."
> L117: "In other cases, all reservations, including basic economy, can change cabin without changing the flights."

Reservation `OWZ4XL` is basic economy. The user instructions (`tasks.json` L2161) are: *"If the agent says your ticket is a basic economy one, you are willing to upgrade to economy in order to make the change."* The gold actions (`tasks.json` L2198, L2218) are:

- `32_3` `update_reservation_flights(reservation_id="OWZ4XL", cabin="economy", flights=[HAT202, HAT232 on 2024-05-21], payment_id="credit_card_9659780")`
- `32_4` `update_reservation_flights(reservation_id="OWZ4XL", cabin="economy", flights=[HAT041 2024-05-21], payment_id="credit_card_9659780")`

The flights of a reservation that was booked as basic economy end up changed. As in task 7, the policy does not say whether L110 applies to the cabin as booked or to the current cabin.

### 3. Airline task 18: checked-bag allowance after a downgrade is unspecified

> L83-86: "If the booking user is a regular member: 0 free checked bag for each basic economy passenger / 1 free checked bag for each economy passenger / 2 free checked bags for each business passenger"
> L95: "Each extra baggage is 50 dollars."
> L123: "The user can add but not remove checked bags."

Gold action `18_0` (`tasks.json` L1114) downgrades `JG7FMM` (regular member, 2 passengers, 3 checked bags, 0 non-free) from business to economy. After the downgrade, the reservation still has 3 free bags. The economy allowance for 2 regular passengers is 2. The policy does not say whether bags beyond the new allowance become paid, stay free, or block the downgrade. We are not claiming the gold action is wrong, only that the policy does not settle the question.

### 4. Retail: cancelling after a payment-method change refunds more than was paid

No gold task takes this chain. We report it because the environment allows an outcome that the policy text describes differently.

`data/tau2/domains/retail/policy.md`:

> L92: "After user confirmation, the order status will be changed to 'cancelled', and the total will be refunded via the original payment method immediately if it is gift card, otherwise in 5 to 7 business days."
> L106: "After user confirmation, the order status will be kept as 'pending'. The original payment method will be refunded immediately if it is a gift card, otherwise it will be refunded within 5 to 7 business days."

Order `#W1068289` (user `yara_patel_8545`) is pending and was paid 3,453.28 by `gift_card_9105630`. The chain is:

1. `modify_pending_order_payment("#W1068289", "paypal_5398626")`
2. `cancel_pending_order("#W1068289", "no longer needed")`

The resulting `payment_history`:

```
payment gift_card_9105630 3453.28
payment paypal_5398626    3453.28
refund  gift_card_9105630 3453.28   <- from step 1
refund  gift_card_9105630 3453.28   <- step 2, for the original payment
refund  paypal_5398626    3453.28   <- step 2, for the PayPal payment
refund  gift_card_9105630 3453.28   <- step 2, for the refund entry of step 1
```

Paid is 6,906.56 and refunded is 13,813.12. The gift card balance goes from 91.00 to 10,450.84 (+10,359.84, three times the order total). The cause is in `src/tau2/domains/retail/tools.py`: `cancel_pending_order` (L191) loops over `order.payment_history` (L218) and creates a refund for every entry, including entries whose `transaction_type` is already `"refund"`. It also refunds the original payment that `modify_pending_order_payment` (L590, refund at L647) has already refunded.

### Suggested fixes (any one per item would resolve it)

- **Tasks 7 and 32:** either (a) state in `policy.md` that the cancellation and modification rules apply to the cabin at booking time, and change the gold actions of tasks 7 and 32 to a refusal or transfer; or (b) state that a cabin change first is allowed, for example under "Change cabin": "After a cabin change, the reservation follows the rules of its new cabin." Option (b) keeps the current gold.
- **Task 18:** add one sentence under "Change cabin" on bags beyond the new allowance, for example "Checked bags already on the reservation stay free after a cabin change." That matches the current gold.
- **Retail:** in `cancel_pending_order`, refund the net amount still held. For example, iterate only over entries with `transaction_type == "payment"` and skip payment methods already refunded, or compute payments minus refunds per method. Optionally add a test that asserts refunded ≤ paid after `modify_pending_order_payment` followed by `cancel_pending_order`.

### Reproduction

**With τ² only** (from a τ² checkout at `0c69df4`; this is `.scratch/up1/repro.py` in our repo):

```python
from tau2.domains.retail.environment import get_environment
env = get_environment(); t = env.tools
gc = t.db.users["yara_patel_8545"].payment_methods["gift_card_9105630"]
b0 = gc.balance
t.modify_pending_order_payment("#W1068289", "paypal_5398626")
o = t.cancel_pending_order("#W1068289", "no longer needed")
print(sum(p.amount for p in o.payment_history if p.transaction_type == "payment"),
      sum(p.amount for p in o.payment_history if p.transaction_type == "refund"),
      round(gc.balance - b0, 2))
# 6906.56 13813.12 10359.84
```

The airline items can be reproduced by calling each gold action of tasks 7, 32 and 18 from `get_tasks()` on a fresh `get_environment()`.

**With Bylaw** (our CLI, which runs over τ² as a dependency):

```
uv run python -m bylaw audit --domain airline --no-llm -o airline.report.json
uv run python -m bylaw replay --domain airline --hole G2:1ERWZ8 --report airline.report.json  # upgrade -> cancel, both ALLOWED
uv run python -m bylaw replay --domain airline --hole G1:1ERWZ8 --report airline.report.json  # upgrade -> change flights, both ALLOWED
```

The blind search finds the same upgrade-then-cancel and upgrade-then-change chains as tasks 7 and 32 on other basic economy reservations. Each step passes a rule set compiled from `policy.md`.

Happy to open a PR for whichever option you prefer.
