§3 How a hole is found

Muse proposes. Search confirms. The engine verifies.

Muse can't be trusted to say a hole exists, and a brute-force search doesn't know what a forbidden outcome is. Together they cover each other's blind spot.

Muse Spark · max reasoning

Threat model

Reads the whole policy in one prompt and writes the forbidden goals as checkable predicates over simulator state, each with its clause. Proposes plausible attack sequences and the abstract argument classes worth trying.

Bounded search

Exhaustive walk

Breadth-first over every tool-call sequence up to 4 calls, across Muse's argument classes. Every step must comply with a cited clause. Reports coverage, not anecdotes.

Deterministic engine

Executed proof

Each candidate runs in the τ² simulator. A hole counts only if the end state satisfies a pre-registered forbidden goal. No hallucinated holes survive.

CLASS A · CIRCUMVENTION

Counted in N

Every step complies with a cited clause. The end state is an outcome another clause explicitly forbids.

CLASS B · CONTRADICTION

Reported, not counted

Two clauses give opposite verdicts on the same state.

CLASS C · SILENCE

Called ambiguity

The policy doesn't address the case. Never presented as a hole.

  • Forbidden goals pre-registered in a timestamped commit before any search runs.
  • Every Class A trace judged blind by an independent reviewer.
  • Traces filed as a public issue on tau2-bench.
  • Coverage stated exactly: exhaustive over abstract argument classes.
