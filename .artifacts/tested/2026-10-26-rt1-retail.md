# RT1: retail domain plug-in

Branch `feat/rt1-retail`, rebased onto `bylaw/build` at 5e2dd54 (contracts v1.3, EN1 merged).

## Problem and the rule it breaks

Bylaw had a single domain (airline), so it could not show that it works on a policy we did not write. REQ-RT1-1..3 ask for τ² retail as a second domain: a C1 `Domain`, pre-registered goals, and a hand RuleSet that is valid under C2.

## Root cause

Not a bug fix. The one Class A hole this item found has its root in the simulator:
`.context/tau2-bench/src/tau2/domains/retail/tools.py:218`. `cancel_pending_order` refunds every line of `payment_history`, and that includes the `refund` line that `modify_pending_order_payment` appends at `tools.py:639`. The policy allows both calls on a pending order, so a payment switch followed by a cancel refunds three times what was paid once.

## Change

- `bylaw/goals_retail.py`: the pre-registration, in its own commit (made before any chain ran). It defines goals R1-R8 as `(db_before, db_after, chain) -> bool` over snapshot dicts. Each goal fires only on orders the chain changed, and each quotes a line of the retail policy. R5 and R8 are Class C; the rest are Class A. After EN1 merged, the only change was to import `Goal` from `bylaw.domain`; no predicate changed.
- `bylaw/env/tau2_retail.py`: `make_domain()` is the entry point that `bylaw.domain.get_domain("retail")` imports. It returns a C1 `RetailDomain` built on `bylaw.domain.StepResult` and `Goal`:
  - `snapshot` returns `{"users","orders","products"}` keyed by id (v1.1);
  - `call` drops any argument the τ² tool does not take (v1.1);
  - `targets(goal)` returns order and user seeds by status.
- `bylaw/rulesets/retail.json`: 24 hand rules across the 7 write tools, plus `forbidden_goals` copied from the goals file. `bylaw.rules.validate` accepts it. The item rules use `zip` (v1.3) to pair each old item with its new item by position.
- `spike/retail_holes_by_hand.py` and `.json`: 9 candidate chains, each run on a fresh env. `bylaw.rules.check` checks each step against retail.json on the state before that step. A chain that reproduces is replayed 5 times.

## Tests added

`tests/test_retail.py` (14 tests) covers:
- env independence, and a snapshot is a copy;
- conversation facts are stripped, and rejections come back as data;
- the C1 surface and `targets`, through `get_domain("retail")`;
- every goal is false on the untouched DB, and its policy_ref is quoted;
- R1, R2, R3, R4, R6 and R7 each fire on the forbidden outcome and not on the permitted one;
- retail.json has the C2 shape and passes `validate`; it names only retail write tools, its refs are quoted, and its goals match the goals file;
- positional item pairing;
- negative controls: retail.json blocks the direct one-step routes;
- spike H1 is Class A with 5/5 replays, and no blocked chain is counted.

## Out of scope / not done

- The rules cannot see some things:
  - an address modification leaves no trace in the order, so "once per order" cannot be enforced for it (this is H2);
  - explicit user confirmation and authentication happen in the conversation.
- Simulator bug, not used by any goal: `modify_pending_order_items` at `tools.py:583` writes the last variant's price and options onto every modified item.
